# Windows benchmark evaluation

All 48 task IDs reached valid terminal outcomes: **0 PASS, 48 model FAIL**. Infrastructure and initializer errors are retained separately and excluded. Results use `deepseek_flash`, reasoning effort `none`, screenshot-only observations, code adapter actions and history window 3. Each task retains its smaller original cap, up to 180 steps.

This is a mixed-version author evaluation, not an unchanged reproduction of the original benchmark. Thirty-nine tasks retain their original ideas. Four image tasks use asymmetric synthetic graphics and GIMP instead of missing photographs and OpenPhotoEdit. Four navigation tasks use an offline route planner, without real traffic. One driver logout task replaces ungradable transient promotion interactions with explicit account creation, two owned support tickets and logout. Original task definitions are archived alongside the repair provenance. These changes limit comparison with original benchmark scores.

Every valid result includes initializer and grader status, termination, full trajectory and final screenshot. Normal DS failures count as model failures by default. Only explicit infrastructure or benchmark defects trigger exclusion and retest; GPT did not complete formal goals on DS's behalf. The OpenFood wrong-restaurant report was reclassified from a grader exception to FAIL using the shipped restaurant seed; its original ERROR report remains available.

Repairs cover keyboard typing delivery, standalone guest Python startup, application launch paths, environment variable expansion, authenticated OpenBank preparation, Calc first-launch readiness, shipped OpenFood seed lookup and OpenNote endpoint readiness after app launch. An incorrectly ordered intermediate OpenNote readiness check caused a zero-step initializer error; that attempt is excluded and the corrected retest is included.

Final review also found that the two-order OpenFood grader looked for immutable identifiers in mutable storage. Its subsidiary menu, courier and restaurant checks are not reliable in the archived report. The valid FAIL is independently established by zero created orders, no required support ticket and wrong final filters. `openfood-seed-grader-audit.json` documents this limitation; the checked-in seed reader is repaired without repeating DS actions or changing the verdict. Other pre-existing unscored transient interactions remain disclosed in grader metadata.

## Evidence and reproduction

The complete archive is published in the [Windows evidence release](https://github.com/BaoZhuhan/os-omni/releases/tag/windows-handover-20261013). `release-manifest.json` lists ordered chunks and SHA256 hashes. Concatenate chunks as binary data, verify the archive hash and extract. The archive includes effective and excluded attempts, logs, screenshots, experiment state, audit records and original local runner scripts. Credentials are redacted; no VM disks or Python runtime are included. `final-score.json` identifies each effective report and original report hash; archive file-manifest hashes apply to sanitized delivered bytes.

The repaired VM package is uploaded through [HF PR #9](https://huggingface.co/datasets/Cloudriver/OS-Omni-VM/discussions/9), titled `Windows_v5_OPENA_app`, under `Windows_V3` at revision `refs/pr/9`. All 165 files (138,422,420,613 bytes including the manifest) have verified remote SHA256 and sizes. The package preserves the original disk chain and the author-created evaluation baseline, plus a new distribution snapshot `author-windows-hf-ready`. Use the current disks or this new distribution snapshot, never the downloaded old snapshots. The original local VM was kept unchanged.

The distribution runtime uses port `5001` and the published local token `os-omni-author-windows-local-runtime`. VMware encryption and guest password are the published benchmark value `password`; guest username is `User`. Configure host runtime settings accordingly and keep the guest runtime isolated from untrusted clients. Source inputs for the rebuilt image and route tasks are under `C:\OS-Omni\AuthorWindowsV3`. Further distribution boot/GUI validation was waived by the author; file integrity was verified separately. This new distribution snapshot is not the exact final disk state of a historical model attempt.

Original source image: pinned HF revision `3f9fea77da05c16a35c07907a3ab320fff653b12`, `v3.1/windows` (98 files, 91,469,100,647 bytes). The historical evaluated baseline was `author-windows-baseline-ready`; the runtime overlay was redeployed after every reset. The published independent copy retains that baseline's ancestry. An independent rerun still requires local VM path/runtime configuration and environment checks; no additional model runs were performed for this upload.

Portable queue sources are in `scripts/windows`. Set `OS_OMNI_WINDOWS_EXPERIMENT` to an extracted working experiment directory, update its VMX path and local task paths, and supply secrets through the external `.codex/secrets/os-omni-deepseek.json` file. Install repository dependencies and VMware Workstation/vmrun. Keep valid results to avoid duplicate evaluation, or create a fresh experiment for an independent run. Run `scripts/windows/run_windows_queue.py`; it serializes resets, initialization, model execution and formal checks. Never manually interact with the guest during active model execution.

The image and route initializers deploy their checked-in assets. OpenBank preparation uses the shipped published seed. Source/reference hashes, image positive and wrong-transform negative checks, driver ownership checks, and real guest preflight records are included. These bounded checks establish the repaired setup; they do not prove that every original goal is feasible in every app version.
